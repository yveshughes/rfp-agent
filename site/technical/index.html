Billy does the work.
You make the call.

Vultr gives Billy a persistent place to work. NetBird gives the right person secure access to that work.

  2. 02

    Discover the Berkeley opportunity

  3. 03

    Bring your previous response

  4. 04

05 / TECHNICAL Q&A

Decisions we can explain.

Decisions from the September 26 deployment, with the tradeoffs we can explain in technical Q&A. The public site and Billy’s private browser workspace run on Vultr. Model-driven drafting and NetBird access are the next integrations.

Why one small Vultr VM?

Decision: Shared CPU, 1 vCPU, 1 GB RAM and 25 GB SSD in Silicon Valley, at $5/month before credits.

Why: Serving the public site needs little compute. One VM keeps cost and operations simple, and Silicon Valley is close to the SF demo audience. Location is a proximity choice, not a measured latency claim.

Tradeoff: There is no redundancy or autoscaling. Agent processing will need its own capacity measurements; this deployment does not establish a GPU requirement.

Why nginx and plain HTML, CSS and JavaScript?

Decision: Serve the pitch, technical reference and app entry route with nginx on Ubuntu 26.04 LTS. No build step or application runtime is needed for these pages.

Why: The first deployment has a small operational footprint and can be checked independently of the agent workflow.

Boundary: The separate Python workspace API now owns browser jobs, imported PDF text and saved research. Model inference and proposal generation are not connected yet.

How can we reproduce the deployment?

Decision: Cloud-init clones the public GitHub repository, checks out an explicit commit and runs deploy/install.sh ↗. The server checkout lives in /opt/rfp-agent; nginx serves /var/www/rfp-agent.

Why: A commit identifies the exact version deployed. The installer copies only site/, keeping repository and private working files outside the web root.

Verification: Public HTML, JavaScript, Mermaid source and video were checked for HTTP 200 responses and byte-for-byte equality with local files. GitHub pushes require an explicit server update; automatic deployment is not configured.

What caused the first connectivity issue?

Observed: Cloud-init completed, nginx was active and local HTTP returned 200, but public HTTP timed out. Ubuntu’s active UFW firewall allowed only SSH.

Decision: Add TCP port 80 for the public website and preserve the firewall. The installer now adds this rule when UFW is active.

Why: A healthy service and a reachable service are separate checks. We verified both instead of disabling the firewall.

How does this fit with private access through NetBird?

Decision: The pitch is publicly reachable over HTTP at the server’s IP address. It accepts no company documents or account credentials. A custom domain and HTTPS are the next access-layer steps.

Planned boundary: Billy’s workspace service currently binds to loopback and is reached from the Mac through an SSH tunnel. Authenticated NetBird ingress is planned; the API is not exposed through public nginx.

Why: Anyone should be able to see the pitch; company evidence needs controlled access. Public port 80 on this website is not evidence that the planned NetBird integration is implemented.

Why skip paid backups and other add-ons?

Decision: No paid backup, DDoS or extra storage add-ons for this deployment. The running cost is evaluated before promotional credits.

Why: The public site can be recreated from Git and the included assets; private workspace data cannot. Credits help fund the event but do not establish a sustainable operating cost.

Revisit when: The workspace now stores originals and RFP records on the VM. They survive service restarts, but there is no off-VM backup yet. Private object storage, database backups and recovery testing are the next durability work; Git does not contain these documents.

Which presentation dependencies can fail independently?

Decision: Serve the optimized animation locally. Load pinned Mermaid 12.0.0 from jsDelivr and fonts from Google Fonts, with a written workflow and system-font fallbacks.

Why: The site remains readable if those external services fail. The animation has a pause control and respects reduced-motion preferences.

Tradeoff: The diagram still depends on a CDN. A fully offline demo would need bundled diagram rendering and fonts. The animation illustrates the vision, not a recorded agent run or contract award.

How does Billy’s expression reflect real activity?

Decision: Character animations follow live workspace state: discussing when Chats is open, snoozing between tasks, researching, reading documents and waiting for input. Snoozing uses an existing closed-eye frame with CSS breathing and floating Zs; the other states use short video loops. Pending decisions and human browser control take precedence over active work. The animation never serves as evidence that a proposal was sent or won.

Why: You can see at a glance whether Billy is working or needs you. A separate Settings preview lets you inspect the animations without changing the agent’s task. Motion can be paused, and reduced-motion preferences are respected.

Why separate Sources from RFPs?

Decision: Sources holds the agency directory and persistent watchlist. RFPs holds specific opportunities, lifecycle statuses and their original documents. The workspace enforces a configurable watched-source allowance on the server.

Why: One agency can publish many opportunities. A limit on followed agencies gives subscription tiers a clear unit without limiting access to the directory.

Boundary: Watching queues a public-source check; the private Vultr service repeats checks hourly. Every discovered candidate stays in All opportunities, including weak matches. Berkeley, East Palo Alto and Siskiyou County have tested listing adapters; other portals use conservative discovery and show partial coverage when completeness is uncertain. Billing and external notifications are separate work.

What does response progress measure?

Decision: Give each RFP a Files tab and editable response sections. Store drafts, per-section checklists, and discussion notes on the Vultr VM. Section percentages measure saved checklist completion; total progress uses all response checklist items.

Why: Missing information stays visible beside the section it belongs to. Files retain their original evidence, and version checks prevent one session from silently overwriting another session’s saved section.

Boundary: Progress is a manual workflow measure, not verified RFP compliance. The initial sections are editable suggestions. Contextual discussion keeps messages with each section. Meta voice/chat can be enabled with server credentials; automatic requirement extraction remains separate. Drafting never submits the response.

Why Gemini Live for Billy’s voice conversation?

Interaction: “Discuss with Billy” opens Chats. The conversation stays in the center; reusable facts and queued actions appear under Discussing on the right. Activity and Decisions remain available beside it.

Recommendation: Gemini Live combines spoken responses, interruptions, transcripts, and tool calls. Muse Voice Transcribe is a strong transcription component, but needs a separate conversational model and voice output. For a natural conversation with Billy, Gemini Live is the closer fit.

Current implementation: Typed guided discussions save company facts and scoped RFP notes, and persist learnings and follow-ups. An optional Meta push-to-talk adapter returns an editable transcript before Send. Gemini Live still needs credentials and integration; neither provider has been validated live in this workspace.

Action boundary: User-reported facts remain distinct from evidence. Accepting an insurance research offer creates a to-do item; it does not buy a policy or submit a bid.

How does Billy build a company profile from conversations?

Decision: Organize reusable company facts by RFP requirement: company essentials, registrations, experience, team, insurance, compliance, pricing, and references. Scoped conversations update the corresponding fact in SQLite. Original documents remain available under Documents and Artifacts.

Why: A statement from chat is useful context, but it is not proof. Each fact distinguishes information reported by the user, an unknown, a reported gap, and linked documentary evidence. Every citation keeps the original PDF page, and a correction clears the old evidence link.

Insurance example: A missing-coverage answer prompts an offer to research options; accepting creates a queued follow-up. A yes or uncertain answer queues verification. Neither path claims a policy has been verified or purchased. Completing a task does not change a fact’s evidence status.

Current scope: Guided profile conversations, evidence linking, and saved follow-ups work. A reported $1M limit and Hartford insurer can become separate facts; questions and ambiguous dollar amounts do not become verified policy data. Independent coverage verification and autonomous task execution require further integrations. The $5M walkthrough is illustrative, not a requirement inferred from a live RFP.

How does Billy rank the watched-source feed?

Decision: Separate discovery from pursuit. Read listing pages and their pagination, retain every discovered RFP, download linked PDF originals, and rank readable opportunities against company capabilities. “Pursue RFP” adds a bid to My RFPs without cloning its documents or response.

Why: A weak fit should remain visible. Scores explain shared terms and link to company evidence. The current deterministic score weights title overlap 65% and body overlap 35%; it refreshes when company facts change. No paid model dependency is needed for this first ranking pass.

Boundary: This is preliminary keyword matching, not semantic evaluation, verified eligibility or a win probability. Missing company facts or unreadable details receive no score. Scans report access errors and partial coverage; they retain previous evidence if a refresh fails. The page budget is 100 listing pages, PDF extraction is limited to 100 pages per document, and complete originals remain available for review. Checks use public GET requests and never submit portal forms.

Where are RFP originals and pipeline statuses stored?

Decision: Preserve complete original PDFs on the Vultr VM and link them to RFP records in SQLite. Store the source URL, download time, content hash and extracted page range. Originals can be reviewed or downloaded from each RFP; table columns can be searched, filtered and sorted.

Why: Evidence stays attached to the opportunity across browser sessions. Extracted text never replaces the original, and a repeated import can reuse the same file.

Boundary: This is private, single-owner VM storage reached through the workspace connection. Object storage and off-VM backups are not configured. Status changes are manual records of progress, not proof of a submission or award. An authenticated access layer must precede broader sharing.

Where does Billy’s browser actually run?

Decision: One Chromium session runs as the non-root Billy service on the existing Vultr VM. The Mac displays screenshots and sends explicit click, type and scroll actions. It is the same session when you take control and hand it back.

Why: Research execution and saved work live together on Vultr. SQLite keeps page captures, source checks, document imports and activity across refreshes. The browser context itself is temporary.

Scope: This is a single-owner workspace. Source search and PDF text extraction are implemented; model-based drafting is not yet connected. The navigation sections use plain JavaScript, continuing the site's small build footprint.

How are browser actions bounded?

Decision: Chromium’s sandbox stays enabled. A narrowly targeted, root-owned browser profile provides the Ubuntu namespace permission it needs. Network checks reject private addresses and non-web schemes; WebSockets and service workers are disabled.

Human control: Form submissions pause for approval. Other network writes require a one-use approval. Taking control prevents Billy from starting a competing navigation.

Tradeoff: This is not a complete hostile-code isolation claim or a universal detector of side effects. Authenticated portal submissions and untrusted document processing need additional validation. A blocked page is recorded as a failure, never a successful review.
